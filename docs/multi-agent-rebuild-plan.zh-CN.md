## 1. 已确认的方向与文档作用

用户已经确认：

- 基于 Argus 的部分代码和 Prompt 组织方式，重建自己的研究组织与控制政策。
- 不再将新角色映射到原有 Manager、Planner、Engineer、Reviewer 链。
- 不再兼容原有 `direct`、`staged`、vertical 阶段编排或固定十二选一政策。
- 新系统首版只保留一套业务工作流，不建设旧模式与新模式并存的 mode 框架。
- 优先建设 **CLI + tmux 操作入口**，不先开发新的 Web 或桌面界面。
- 保留完整的授权、讨论、执行、评估、停止、恢复和归档闭环；简化的是旧政策和无关功能，不是必要控制边界。

本计划依据用户提供的：

- 《多 Agent 讨论与运行规则》，规则 v2，2026-10-09。
- 《Linux 多 Agent 研究与执行工作流：完整搭建蓝图》，设计稿 v3，2026-10-09。
- 本会话确认的完整重构方向和 CLI + tmux 决定。

本文件自包含记录实施所需的关键政策，不要求未来 AI 访问本次会话的附件绝对路径。
如用户随后提供原规范的修订版，讨论、评分、放行、监督、黄牌和文件管理政策以用户确认的修订为准。
本文件中的代码布局和建设顺序是工程建议，不是不可调整的业务规则。
发现实质矛盾应询问用户，不能自行选择较宽松的授权解释。

## 2. 首版范围与不做事项

### 2.1 首版目标

在单台 Linux 主机上，以一个控制器和一种明确选定的 Agent CLI，完成：

**目标与授权 → 调研和角色配置 → 独立提案 → 独立评审 → rebuttal → 双报告 → 批注与放行 → 项目分配 → 专家确认 → 隔离执行 → 独立评估 → 调整、停止或交付 → 归档回收。**

支持同一轮多个方向在有限资源下并行；角色按需启动，不要求常驻。
第一类真实任务的评估器可以专用实现，不先建设适用于所有领域的插件平台。

### 2.2 首版不做

- 多机调度、控制面高可用、多租户和复杂自动学习调度。
- 同时验证所有旧模型后端、操作系统和领域功能。
- 保留旧四角色编排、旧阶段体系、十二选一和新工作流两套执行路径。
- 用单个模型模拟多人发言冒充独立 Agent。
- 把 tmux 窗格输出、模型同意或工程师完成声明当作成功依据。
- 新建漂亮聊天界面、Web 管理台、桌面安装包或无关集成。
- 给每个角色永久创建完整环境、容器镜像或无限日志目录。
- 默认增加 dry-run、复杂参数框架、通用工厂、无用兼容层或未来占位接口。
- 在没有明确授权时安装部署、启动服务、调用付费模型、执行长编译或进行 GPU 实验。

现有工作环境可能是 Windows；这不代表已经具备 Linux、tmux、容器或 GPU 验收条件。
无法在目标环境检查的能力必须标为未验证，不能以 Windows 静态检查代替 Linux 运行结果。

## 3. 开始实施与开启自动化所需输入

可以先建设账本和协议，不必等待所有设备参数；但不能用缺失参数启动无界自动任务。

| 输入 | 需要确认的内容 | 缺失时的处理 |
|---|---|---|
| 第一类真实任务 | 目标、非目标、当前基线、典型输入和期望交付 | 不猜测研究领域；先完成无领域假设的基础任务 |
| 评估合同 | 定向正确性快检、整体指标、比较条件、重复规则、噪声和退化判据 | 可讨论；正式收益判定与黄牌阻塞 |
| 首个运行后端 | CLI 名称、实际版本、模型配置、认证方式、事件与恢复能力 | 不默认把当前聊天模型或某个 CLI 当成部署选择 |
| Linux 资源 | CPU、内存、GPU、磁盘、文件数容量、可用权限和并发 | 不能自动启动可能无界占用资源的作业 |
| 本轮预算与期限 | 模型、计算、讨论、监督、集成、存储等额度与截止条件 | 不解释为无限额度 |
| 数据与网络权限 | 私有材料范围、批准的模型和检索出口、允许外部服务 | 不外发私有材料或开放任意网络 |
| 讨论配置 | 专家名单、每专家最大方向数、评审名单、rebuttal 轮数 | 不替用户选择轮数，不假装完整委员会已经评审 |
| 报告交付渠道 | CLI + tmux 中何处交付通知、如何确认可访问和交付成功 | 不启动 20 分钟计时 |
| 存储与保留 | 工作区、日志、检查点、归档和主机余量 | 不能开启无界写入的无人值守任务 |

询问时一次只询问一个会影响当前实施的决定。
不要求用户提供密码或密钥正文；配置认证应通过批准的本地方式进行。

## 4. 代码复用与淘汰边界

### 4.1 按实际依赖提取可复用能力

| 当前代码区域 | 复用目标 | 必须重新核对 |
|---|---|---|
| `argus_skill\agent_cli`、`argus_skill\adapters` | 首个后端的启动、流式事件、结果与会话恢复 | 旧角色、全局配置、权限默认值、取消与费用语义的依赖 |
| `argus_skill\core\ports.py`、`run_gateway.py` | 统一调用边界及独立执行句柄的设计 | 不把旧 OperatorContext 和旧角色政策整体带入 |
| 进程身份和停止工具 | 精准实例定位、子作业核对和终止 | 目标平台的真实行为；不能按进程名批量停止 |
| 用量和计价工具 | 提取真实调用用量、增量费用和未知状态 | 原有统计与准入不等于严格预留或精确账单上限 |
| `argus_skill\core\role_session.py` | 从持久资料恢复、明确会话 ID、上下文轮换的方法 | 多位专家、不同 idea 的实例隔离；不共享旧角色胶囊 |
| `argus_skill\roles\prompts` | 分层 Prompt 组织方法 | 当前解析器绑定旧角色与 vertical，内容和绑定需要重写 |
| 现有 pytest、Ruff 等工具 | 定向验证与适用的底层测试 | 不把大量旧领域回归当作新系统的默认验证负担 |

能直接用的底层实现优先复用；与旧编排耦合严重时提取必要部分，不保留整个旧系统只为复用一个函数。
不要先写大量通用 adapter；先接通实际选定的后端，再根据真实需求扩展。
复用代码保留 MIT 许可证和所需版权声明。

### 4.2 不进入新执行路径的旧业务

- 旧 Manager、Planner、Engineer、Reviewer 的调用顺序与权限映射。
- `LifeSupervisor` 的旧持续规划、阶段推进和终结政策。
- 旧 direct/staged 解析、vertical 分类和领域阶段契约。
- 固定十二条路线、十二份评审、选择一个赢家的研究选题器。
- 旧 Team 编排、故障计数或 GC 与新资源、黄牌、引用回收规则之间的隐式等价。
- 旧技能自进化、论文流程、消息集成等非首版要求。

允许建设期间旧代码尚未删除，但新控制器不能调用旧业务编排。
最终切换后不保留两套可执行核心，也不依赖 legacy mode 开关决定实际政策。

### 4.3 必须保留的通用提效与 token 管理能力

2026-10-09，用户补充要求：重构后保留原 Argus 中通用的提效、token 节约和安全机制。
以下条目依据当前源码和直接相关文档整理，是需要在新路径中落实的能力，不要求原样保留旧类或旧角色。
旧文档的历史测量不代表新系统已取得相同效果；本次仅核查实现，未运行模型或安全隔离实验。

| 能力 | 当前可参考的依据 | 新系统的保留要求 |
|---|---|---|
| 单一任务合同与按引用交接 | `life\context_packet.py` | 传递一个权威合同及角色相关引用，不重复塞入用户请求、计划、检查点和完整聊天；关键原文按需读取 |
| 同角色会话续接与静态/增量 Prompt | `core\role_session.py`、`reviewer\_core.py` | 相同角色实例、任务范围和配置下使用明确会话 ID；恢复时只发送必要增量，静态规则不每轮重发 |
| 上下文轮换与缓存计量 | `core\role_session.py`、`core\token_usage.py` | 配置、目标或分支改变以及质量信号出现时明确轮换；区分缓存输入、新增计费用量和真实上下文占用 |
| 知识与 Skill 按需加载 | `skills\loop_skill_library.py`、`docs\ROLE_SESSIONS_AND_SKILLS.md` | 先给允许范围内的索引或路径，确认匹配后读正文；本角色资料优先，不注入全库，不恢复旧 vertical 依赖 |
| 长期指令去重与范围投影 | `core\operator_context.py` | 相同有效长期规则只投影一次；保留最新有效版本、撤销、角色和任务范围，不把独立请求或一次性动作合并 |
| 最小工具与 MCP 集合 | `agent_cli\copilot_acp.py`、`agent_cli\_sandbox_commands.py` | 按任务只暴露必要工具，减少无用工具 schema 和越权面；不默认加载环境中的全部 MCP、指令和工具 |
| 已成立检查的有限复用 | `docs\PRINCIPLES.zh-CN.md`、`docs\token-consumption-fixes-2026-09-06.md` | 输入、协议和必要执行条件未变时引用已有有效证据，不创建重复验证任务；条件变化或新矛盾出现时失效 |
| 等待退避与重复状态抑制 | `life\supervisor\_idle_cycle.py` | 等待用户、报告窗口或已知阻塞时由程序等待与唤醒，不调用模型反复询问同一状态；变化即时显示，普通重复状态有界汇总 |
| 机械事实由程序处理 | `docs\model-decision-boundary.md` | 时间、标识、路径、状态、费用与评分汇总由程序提供，不消耗模型 token 重建这些事实 |

实施约束：

- 会话复用不能跨专家、评审、idea 或互相隔离的权限范围，不以缓存命中换取首轮泄漏。
- 稳定前缀和明确续接有助于减少重复输入与利用供应商缓存，但不保证所有后端缓存命中或账单降低。
- 已缓存输入仍可能占用真实模型上下文；不能用较低计费量推断上下文不会满。
- 新会话获得完整必要合同与资料入口；续接失败显式记录，再按获准流程恢复，不静默丢失任务依据。
- 缓存或恢复元数据的可选写入失败可以告警；授权、评分、放行、作业、费用和关键证据写入失败必须阻塞相关动作。
- 不为省 token 硬截断必要输入，不照搬旧会话轮数或 token 常量；轮换须符合选定后端能力与本轮实际需要。
- 指令去重只处理真正相同的长期指令，不把“再测一次”或两次独立批准误认为重复。
- 复用有效检查不等于缓存科学判断：不得用旧评分替代用户要求的 N 轮独立复评，也不跨 idea 缓存监督结论。
- 只读角色若需要提交提案或评分，通过受限提交通道完成；不能为提交结果而获得任意工作区写权限。
- 不复制后端特定的工具名技巧或静默配置替代；所选 CLI 不支持必要工具限制时明确阻塞。
- 不因空队列自行制造工作，不恢复旧 Planner 的无限循环；已有进度检查仍按 60 分钟政策执行。

### 4.4 必须保留的通用安全与运行可靠性能力

| 能力 | 当前可参考的依据 | 新系统的保留要求 |
|---|---|---|
| 目标所有权与版本化授权 | `core\project_contract.py`、`docs\goal-contract-authority.md` | 约束的可机械检查程度不决定谁能修改；目标、非目标和用户所有的条件不得被项目经理自行放宽，批准绑定当前对象与版本 |
| 工具权限和只读执行 | `agent_cli\_sandbox_commands.py`、`agent_cli\copilot_acp.py` | 评审、监督与其他只读工作不能修改被核验实现；额外参数、环境和恢复会话不能扩大已授予权限 |
| 控制面与工作区隔离 | `core\sandbox.py` | Agent 不能修改控制器源码、配置、账本、评估器、共享环境或其他任务目录；不把原来的不受限运行默认值带入新系统 |
| 凭据脱敏 | `core\secret_guard.py`、`adapters\agent_cli_backend\_io_log.py`、`_exec_finalize.py` | 事件、错误、结果摘要、tmux 显示及日志出口统一处理已知凭据与高置信模式；秘密不能进入源码或普通报告 |
| 费用可观察与未结对账 | `core\cost_control.py`、`adapters\agent_cli_backend\_budget_monitor.py` | 保留运行中费用和可观测的关联子 Agent 用量，正确处理累计、迟到、未知用量与取消；不复制历史默认金额 |
| 工作区独占与有限并发 | `core\workspace_lease.py`、`team\curator.py` | 同一可写工作区不被两个执行者同时占用；并发计入真实活跃实例和未结作业，不因心跳尚未出现而重复启动 |
| 精确进程身份与停止确认 | `core\process_identity.py`、`core\process_stop.py` | 对准确实例和关联子作业操作；避免 PID 复用误杀，确认实际停止后才释放资源 |
| 持久事实与显式错误 | `core\pipeline_state.py`、`life\context_packet.py` | 保留原子的持久写入思路，迁入单一新账本；不靠聊天恢复批准，不把损坏状态或写入失败降级成成功 |

重要边界：

- 当前 `core\sandbox.py` 所定义的 Engineer 沙箱默认关闭，是可选择启用的能力，不代表原仓库已在所有后端默认提供完整隔离。
- 当前只读工具控制具有后端和版本差异；源码存在相关分支不等于已验证目标机器的所有绕过路径。
- 新系统不继承自动绕过批准或沙箱的启动选项；边界无法落实时不开放相应无人值守工作。
- 脱敏是辅助措施，不是私有数据出口授权，也不保证识别任意秘密；不要把本次代码核查称为漏洞审计或安全认证。
- 不为脱敏改写唯一原始测量、测试样本或上游资料。发现泄露时冻结受影响交付，按权限保留证据并生成明确标记的受控脱敏展示或交付版本。
- 已知凭据、已识别模式、无法检查的内容和处理失败应明确区分；不能把未扫描到理解为绝对无秘密。
- 工作区占用保护按实际可写范围生效，不能用整个项目大锁把允许的独立并行全部串行化。
- 费用轮询存在在途请求与遥测延迟，不能作为严格供应商账单上限；严格无人值守准入仍按第 12 节落实。
- 复用安全代码时保留真正的权限和持久边界，不原样复制无依据的重试、宽泛捕获或成功形状的回退。

### 4.5 通用能力的保留核对

在清理旧代码前逐项记录第 4.3、4.4 节对应的新实现位置及适用条件。
“已删除旧角色类”不是删除这些通用能力的理由；“仍可 import 旧工具”也不代表新路径已接通。

验证范围保持精简：

- 优先复用 `tests\test_role_session_lifecycle.py`、`tests\test_role_session_auto.py`、`tests\test_secret_guard.py` 中仍适用的测试及相关已有预算、权限测试。
- 用少量集中检查验证会话隔离、静态/增量行为、规则去重、工具限制、脱敏和工作区冲突。
- 经用户授权后，在首个真实后端的匹配任务上记录输入/输出、缓存 token、模型调用次数、耗时、费用和验收结果。
- 不设没有依据的固定节省百分比；避免减少 token 却遗漏依据、泄漏私有上下文或降低验收质量。
- 未在真实后端或 Linux 环境检验的缓存、只读和沙箱行为明确标为未验证，不为此默认启动更多模型或整仓回归。

## 5. 最小架构与权力分工

### 5.1 单应用内的五块职责

| 部分 | 职责 |
|---|---|
| 状态与账本 | SQLite schema、短事务、状态转换、事件、派发意图和回执 |
| 研究组织 | 角色资料、可见性、提案、评分、回应、报告和会诊 |
| 控制器 | 输入处理、阶段推进、授权、准入、调度、监督触发和恢复核对 |
| 运行器与评估 | Agent CLI、隔离作业、可信事件、用量、冻结产物和独立测量 |
| CLI 与 tmux | 用户输入、状态、报告、批注、日志、接管与停止入口 |

它们是职责边界，不要求五个服务或固定数量的源文件。
默认一个控制器实例；CLI 向控制器提交动作，不在每次调用时另启动一份调度循环。
没有外部消费者时，不引入 Kafka、Redis、独立队列平台或第二个调度器。

### 5.2 谁决定什么

- **用户：**目标、非目标、硬约束、总授权、预算扩大、数据出口和最终验收。
- **调研者与蒸馏者：**在本轮批准的资料范围内调研基线、替代方法与反例，形成方法卡和角色指令；不运行候选实验、不授予工具权限。
- **主持人：**讨论组织、材料分发、回应流程和双报告；不批准自己的研究结论。
- **专家：**机制、证据、技术指导、最小实验和会诊修正；不自行增配资源。
- **评审专家：**独立评分、三句评语和阻断项；不公开提案、不指挥工程师。
- **项目经理：**在授权内决定排序、分配、继续、暂停、停止和交付安排。
- **工程师：**实施、运行获准实验和真实提交；不自我认证、不改评估门槛。
- **监督：**解释可信进度、成本、证据和整体收益；不自行调度无关项目。
- **控制器与可信运行器：**落实权限、时间、状态、配额、作业生命周期和归档。

评审委员会只含评审专家。
监管工作组织可以包含项目经理、工程师和监督，但工程师不是自己成果的独立验证者。
项目经理不能豁免预算边界或已确认的真实性违规。
不另外恢复旧 Planner 作为第二个任务决策中心：经理提出可执行分配，程序校验和排队。

## 6. 持久对象、状态和恢复

### 6.1 数据关系

**项目 → 研究轮次 → idea 及版本谱系 → 任务 → 尝试 → Agent/实验/评估作业。**

- 项目保存长期目标和权限，不等于模型会话。
- 研究轮次绑定本轮合同、名单、讨论配置、预算和报告。
- idea 保存方向与谱系；参数微调、换工程师或换 Prompt 不自动产生无关新谱系。
- 任务是可验收单元；一次本地修复不必重新召开完整讨论。
- 前置调研和蒸馏任务直接属于研究轮次，不要求先有 idea 或推理代码；正式实施任务关联已放行的 idea 版本。这里的前置/实施阶段不是恢复旧 direct/staged mode。
- 尝试绑定确定输入、角色配置、资源、代码与运行身份。
- 作业是准确的实际运行单元；训练和评估子作业不能只藏在 Agent 聊天中。

数据库还需记录提案版本、各轮评分、回应、用户批注、放行范围、分配合同、评估、黄牌、真实性核查和产物引用。
不为每种记录先设计独立服务；表和关系只围绕真实操作建立。

### 6.2 状态规则

- 讨论和执行有独立状态；工程师声明完成只能申请评估。
- 报告提交后进入批注等待；暂停、否决、授权缺失、证据不足都有显式状态。
- 任务完成、idea 被接受、研究轮次结束、用户最终验收不能混为一个 `done`。
- 区分方向被反证、执行或基础设施失败、人工取消、预算停止、存储阻塞和真实性违规。
- 生产者退出或失去对应产物写权限后，才允许评估冻结的产物。
- 不接收允许转换表之外的任意状态跳转。

### 6.3 数据库与真实进程之间

SQLite 是新系统唯一业务账本；不继续镜像维护旧 backlog、pipeline 文件和新数据库的两份权威状态。
数据库事务内不等待模型、启动容器或运行实验。
有副作用的派发和停止记录持久意图与回执，使用准确作业身份核对。

重启时先禁止新派工，核对运行实例、未完成意图、批注、资源占用和未结费用，再恢复准入。
租约或心跳失效不意味着旧作业已结束；状态不明先恢复核对，不启动替代昂贵作业。
重复请求和重复结果不能重复启动、结算或发牌；优先使用已有事件、作业和版本身份。
不声称外部动作天然“恰好执行一次”，不盲目重放状态不明的副作用。

数据库放本地磁盘，不放 NFS 或同步盘；使用 SQLite 一致性备份方式，不能仅复制活跃主文件而漏掉 WAL。
备份恢复同时核对被引用产物和配置；数据库不可用时关闭准入，不临时把聊天当账本。

## 7. 角色 Prompt、技术资料与上下文

所有角色使用四层输入：

1. 共享合同：目标、真实性、验收、授权和资源边界。
2. 角色指令：职责、方法论、失败模式和必要输出。
3. 知识包：核查过的来源、方法卡、反例、代码和适用条件。
4. 当前任务：本轮或本 idea 的输入、阶段、资源和产物位置。

专家配置先来自资料调研，再蒸馏方法；不只写“天才专家”等人格描述。
角色数量、模型和专家方向按任务登记，不写死庞大团队。
同一讨论轮次和执行阶段固定角色配置版本；更改模型、Prompt、工具或知识包要显式记录影响。
不同专家、评审、idea 和执行尝试使用独立上下文，不能只按一个通用角色名复用同一会话。

恢复时读取角色指令、当前合同、结构化进展、相关技术资料和必要证据索引。
不广播全量聊天，也不截断必要任务依据来满足任意 token 上限。
讨论证据留在持久账本；会话回收不意味着删除证据。
两张黄牌后的专家冷启动携带停止档案，不续接终止的 provider 会话。

自然语言用于推理与说明；必要行动和评分使用最小可校验字段。
时间戳、路径、版本、实例身份和授权状态由程序生成，不能要求模型复述并把它当事实。
外部材料不能升级为权限指令；实际 system prompt、工具限制和恢复语义以所选 CLI 能力为准。
不支持必要权限语义时明确阻塞，不能把普通用户消息冒充系统级隔离。

## 8. 讨论、评分、回应和报告

### 8.1 开始前

准备目标、非目标、基线、实验约束、授权、角色名单、失败档案和讨论配置。
主持人向用户确认非负整数 rebuttal 轮数：

- `0`：首轮提案和评分后直接报告。
- `N`：首轮之后完成 N 次“回应或修订 → 独立复评”。

首轮不算 rebuttal；追加轮数重新确认。
预算耗尽或运行失败可以提前结束，但报告写明实际完成轮数和缺失项。
每位提案专家至少提出一个具体可检验方向；每个方向分别记录和评审。

### 8.2 独立性和可见性

- 调用可并行；展示先各层专家、后协同优化专家。
- 专家首轮不能读取其他提案，包括 co-opt 专家。
- 评审提交锁定前不能读取其他评审的本轮评分。
- 评分汇总后，仅将本 idea 的评分、评语、阻断项交给对应专家回应。
- 不要求所有专家开放互辩或达成一致；主持人不能冒名补写缺失提案或修改评价。
- 可见性通过材料分发、目录与读取权限落实，不能仅依靠 Prompt 禁止。

### 8.3 提案与共同评分

提案包含问题定位、证据、机制假设、技术细节、预期与不确定性、代价、接口、最小判别实验、失败条件、步骤和资源。
联合方向还需组件分工、共同接口、联合变量与端到端验收。
无收益估计依据时写“待测”，不编造精确改善数字。

| 评分维度 | 权重 |
|---|---|
| 目标收益与机制价值 | 30% |
| 技术可行性与细节 | 25% |
| 证据与可验证性 | 20% |
| 系统影响与协作兼容性 | 15% |
| 成本与资源合理性 | 10% |

每维度 0–5 分，允许 0.5 步长。程序按权重计算推荐度。
共同尺度：0 为明确不满足或被反驳；1 为重大缺口；2 为重要条件不足；3 为足以开展有界实验；4 为扎实且风险具体；5 为证据、细节、边界充分支持。
无法判断的关键技术点标记需补证，不能用 0 分冒充判断。
展示一位小数；排序使用未提前舍入值。
各评审等权平均，同时保留范围；最大最小推荐度差至少 2 分标记显著分歧。

每位评审每个 idea 写三句：**价值、风险、行动**。
阻断项单独记录，不能被平均分抵消。
缺失评分不填 0；不设置低于某固定分数自动淘汰的规则。
评分表示值得实验的程度，不是已经取得的性能。

### 8.4 回应与双报告

每次回应逐项说明接受、修改、补证或坚持理由；允许不改方案，但不能不回应。
复评读取最新版、变化和回应，仍独立提交；不无限追加“最后一轮”。

每轮结束生成：

- 长报告：自包含的目标、全部最终 idea、技术细节、评分轨迹索引、来源、阻断、接口、实验、资源和证据入口。
- 短报告：尽量一页以内，突出方向、最终分数、分歧、预期、风险、资源、阻断、长报告位置及窗口起止时间。

长报告不能只有摘要和聊天链接；短报告不能把预期写成实测。
不为每次发言或每位专家额外生成重复报告。

## 9. 双报告后的 20 分钟放行

这是用户已经选择的政策，但只作用于本轮已明确的授权范围。

- 两份报告校验、持久保存且约定渠道的可访问通知成功交付后，才记录开始和截止时间。
- 报告缺失、链接不可访问或通知失败，不开始计时。
- 不要求用户实际打开报告；也不能把写入普通调试日志当作成功通知。
- 明确同意可以提前放行；到期无适用批注记录 `TIMEOUT_AUTO_RELEASE`。
- 自动放行不写成用户认可结论，只移交经理排序和分配，不表示所有 idea 同时运行。
- 本 idea 的批注暂停本 idea；全局或含义不明确的批注暂停本轮。
- 暂停或否决不会因又过 20 分钟失效。
- 实质修订重发受影响报告并重新计时；未受影响范围保持原期限。
- 截止前已可靠接收的批注，即使尚未处理，也必须阻止对应放行。
- 重启恢复原截止时间，先核对输入，再决定放行；不重复移交。
- 启动后收到暂停或撤销，先停止新动作并安全中断对应作业；已发生费用不能假装撤回。

超时不替用户选择 rebuttal 轮数，不扩大目标、总预算、设备、数据出口，也不授权发布、生产部署或最终验收。
没有任何可执行方向时通知原因，不为推进状态强行启动。

## 10. 分配、确认、实验和评估

### 10.1 经理分配与专家确认

经理核对否决、授权、阻断、评审完整性、依赖、输入、资源和既往失败，再决定实施、排队、补证或阻塞。
评分只是参考；资源按阶段分配，优先验证关键假设的最小实验。
缺失必要提案、评分或约定回应的方向默认补证或阻塞，不因超时而假装完成评审。

每个执行合同包含：idea 与谱系、版本、基线、输入、负责人、专家与工程师、接口、阶段、快检、指标、有效测量条件、负优化判据、额度、期限、产物和检查安排。
工程师启动前与专家一对一确认，用自己的话复述关键步骤和不确定性。
技术路线或接口实质变化、首张黄牌或决定性不可行条件触发再确认，不为每条命令召开会议。
联合项目由牵头专家确认共同接口，各工程师再确认各自任务。

### 10.2 执行边界

- 可信运行器启动获准作业；Agent 只能提交申请，不能直接获得全局管理权。
- 工作区按尝试创建；成员拥有独立可写环境，公共数据、基线和环境固定版本只读复用。
- Git worktree 不是安全沙箱；不向执行者暴露公共可写 Git 元数据或远程发布凭据。
- 隔离环境不挂载宿主 home、控制数据库、Docker socket 或主密钥。
- CPU、内存、进程数、GPU 设备、时间与存储限额需要实际落实；不能仅设置环境变量宣称隔离。
- rootless、cgroup 和 GPU 能力根据目标主机核对；无法落实时不开放相应无人值守工作。
- 不默许在宿主机全局安装依赖；环境准备限于批准的本地或隔离范围。

### 10.3 三类检查

| 检查 | 触发与动作 |
|---|---|
| 健康 | 程序持续检查真实实例、费用、资源、权限和时限；异常立即处理 |
| 进度 | 运行项目每 60 分钟检查阶段、产物、阻塞与剩余预算；以启动时间为锚点 |
| 效果 | 有有效阶段产物或完成上报时，冻结产物，执行快检和可信测量 |

完成上报不无限推迟下次小时检查；非运行状态不开空会议。
定时与完成事件重合时，同一产物评估只处理一次。
没有终端新文字不等于作业失效；无数据不能判成功或负优化。

快检使用已有少量受影响检查或可信参考，清单和容差事先约定。
状态区分通过、失败、未执行、结果不明；只有通过且测量有效才能判断收益。
“通过约定快检”不等于全面证明正确。
评估程序、隐藏数据和判据不由执行工程师修改；隐藏数据不进入执行容器。
保存代码、配置、协议、资源条件、命令、原始结果、重复与异常，不只保存平均分。
获胜方向可在授权内追加资源，但最终比较仍保持公平资源条件或明确声明资源变量。

## 11. 黄牌、真实性和停止

### 11.1 有效负优化与谱系黄牌

负优化须相对冻结基线，在可比较条件下通过快检并取得足够有效观测，超出事先约定的噪声或退化判据。
联合方向看整体指标，不因某层局部变慢处罚。
不发牌的情形包括无提升但无可信退化、证据不足、噪声内波动、基础设施故障、OOM、快检失败和获准中间探索状态。
这些情况仍可修复、阻塞或预算止损，不表示无限继续。

监督提交依据，可信程序核对可机械核对的判据，经理确认登记。
同一有效评估最多一张牌；换人、换 Prompt、微调参数、取得后续正收益不清零。
真正的新机制要记录与旧假设差异，不能换名清除历史。

第一张：立即暂停新工作，准确中断关联作业，保存可用状态，专家与工程师会诊，经理批准有界调整后创建新尝试。
第二张：终止该谱系项目和对应会话、请求及子作业，核对资源与费用，归档停止原因和两次证据，回收相关上下文。
专家以冷启动身份进入待讨论队列，不自动开始新一轮或获得新预算。
处罚错误可依据新证据撤销，但保留原记录、理由和新尝试关系。

### 11.2 真实性核查

所有角色区分已核实、推断、预期、未执行、失败和未知。
禁止虚构来源、操作、测量、检查、用户决定或评审意见，以及篡改指标、基线和必须保留的失败样本。
普通 bug、诚实失败或明确标注的预测不自动构成违规。

疑点先冻结受影响结果与相关高风险动作；核对可信日志、原始资料和产物。
确认违规后立即终止违规实例并撤销权限，记录 `TRUTH_VIOLATION`，不走黄牌或等待下次检查。
不以另一个 Agent 的指控代替事实，也不推测主观恶意。
只处罚有证据违规的角色，核对污染的报告和决定；不自动给被它评审的 idea 发牌。
证据不足时保持待核查；无法核实的成功不能用于奖励资源。

### 11.3 停止协议

先持久记录停止原因并关闭新动作准入，再对准确实例执行中断或终止。
非紧急情况可在有界且获准的宽限内保存检查点；确认违规等紧急情况优先撤销和终止。
核对 Agent、子进程、实验、评估和远程作业，确认退出后才释放可确认的资源。
未知费用继续待对账；不把关闭 tmux 窗格当作停止完成，不按进程名批量杀。

## 12. 预算、存储与归档

### 12.1 预算

模型、计算和时间分别计量，讨论、评审、监督和集成都计入本轮。
启动前预留，可靠用量后结算，未知用量不计零，状态不明不立即释放全部预留。
CLI 累计费用先确认语义再取增量；不重复累计恢复会话的历史成本。

严格金额上限要求发出请求前有可信估算与受控准入，并保留在途请求及账单安全余量。
需要模型出口控制时优先使用组织批准的现有网关；不能通过无限轮询 CLI 费用宣称严格控费。
无法计量、约束或撤销必要高成本能力时，阻塞相应无人值守执行。
CPU/RAM/GPU 和并发准入计入主机容量，给控制器和系统留余量，不能靠主机 OOM 调度。
扩大总预算或权限需要用户决定，不能用 20 分钟政策增额。

### 12.2 必要归档和回收

长期保留技术方案、谱系、确认合同、代码或完整补丁、配置与环境版本、协议、快检、原始指标及必要结果、调整轨迹、处罚及撤销、停止原因、费用和放行记录。
技术档案持久保存；恢复只加载必要索引，原始内容按需读取。
公共输入只读共用；不为每个 Agent 重复下载数据或按身份永久创建镜像。

明确工作区字节与文件数、日志分片与期限、检查点数量与大小、归档额度。
主机计划同时覆盖共享数据、镜像、挂载、缓存、容器日志、数据库/WAL和备份，而非只限制输出目录。
超限或写入失败显式进入 `STORAGE_BLOCKED`，不静默丢必要结果，不把截断归档报告为成功。

回收前确认：

- 关联作业已停止，或确认不再依赖该对象。
- 必要成果已完整归档并可读取，归档不是指向待删源文件的失效链接。
- 无报告、评估、检查点、其他项目或有效恢复方案依赖唯一对象。
- 不属于仍需保留的处罚、真实性、复现或争议证据。
- 删除目标为精确登记且在批准范围内的路径或实例。

归档失败保留唯一源文件并阻塞回收。
禁止仅按年龄判无用，禁止宽泛通配符或全局 Git/Docker 清理。
普通日志轮转前提取必要关键证据；不默认保存每一步完整环境或模型快照。

## 13. CLI + tmux 入口

### 13.1 CLI 的必要动作

设计并实现一个一致的入口，覆盖：

- 创建项目和本轮，提交或读取合同与配置。
- 启动控制器、检查就绪和显示状态。
- 回答待决问题，包括 rebuttal 轮数。
- 读取长短报告、提交本轮或 idea 批注、明确放行或拒绝。
- 查询任务、作业、费用、资源、结果和关键日志。
- 暂停、获准恢复、取消，区分停止新派工与停止正在运行的作业。
- 人工接管、结束接管、读取归档和待讨论专家队列。

具体命令名在实施时统一设计；以上是动作要求，不是当前可运行命令。
先做少量清晰子命令，不搭建复杂命令框架或把全部数据库对象暴露成 CLI CRUD。
副作用走同一控制器校验；CLI 输出真实状态，不把请求成功当成作业已经停止。
用户批注在入口可靠接收时持久登记时间和范围，不能等模型处理完才记接收时间。

### 13.2 tmux 的职责

建议按需展示控制台、讨论、选中执行任务日志和告警。
不固定窗格数量，不要求每个角色永久在线。
输出优先来自可信事件和日志，不抓屏正则猜测任务状态。

tmux 管理终端和人工观察；控制器管理任务事实、权限、费用和生命周期。
用户 detach 或 SSH 断线不应丢失账本；日志观察窗格关闭不应误杀受管实验。
关闭承载控制器的窗格可能结束控制进程，需要明确提示和恢复路径，不能声称 tmux 自动重启程序。
初期可在 tmux 中运行控制器；无人值守部署需要时再提供受支持的服务管理方式，不第一天就新建多个守护服务。

tmux 中默认执行经过控制器的命令；不得靠 `send-keys` 向 Agent 注入指令绕过授权账本。
人工接管先暂停对应自动控制和发送，记录接管状态；退出接管后核对实例、产物和未完成命令。
首版可以先通过接管后的受控命令操作，不要求兼容每种 CLI 的在线会话输入。
必要能力不支持时明确说明，不允许人和调度器同时控制同一实例。

报告通知采用用户约定的 CLI + tmux 渠道；通知回执及报告可访问性必须能核对。
不以窗格“存在”或用户“可能看到”作为启动倒计时的证据。

## 15. 必要验证与上线门槛

使用现有工具；以少量集中测试覆盖关键边界，不为每个模块新建大量 mock、fixture 和测试框架。
确定性状态测试可使用受控时间和运行器替身，但不能把它写成真实 CLI 或 GPU 已通过。

| 场景 | 必须观察到的结果 |
|---|---|
| 同角色续接与配置变更 | 续接只携带必要增量；身份、范围或配置变化时不复用不适用的上下文 |
| 重复长期指令与独立请求 | 长期规则不重复注入，独立任务、撤销和一次性动作不被错误合并 |
| 可选恢复元数据或权威账本写入失败 | 前者明确告警，后者阻塞相关副作用，不报告为已持久成功 |
| 只读调用的额外参数与跨任务读取 | 不扩大权限，不泄漏其他私有提案或修改被验证产物 |
| 凭据进入事件、异常或结果 | 普通日志和 tmux 输出脱敏，必要证据不被无声改写 |
| 两个执行者争用同一可写工作区 | 明确冲突；不同获准工作区仍可并行 |
| 缺轮数、预算、权限或必要协议 | 明确等待，禁止对应自动动作 |
| 首轮提案与未提交评分 | 其他无权角色不能读取 |
| 评分计算、0/N 轮和缺失评审 | 权重、步长、轮数正确，缺失不按零填充 |
| 报告或通知失败 | 不启动批注计时 |
| 截止前收到尚未处理的批注 | 阻止对应范围放行 |
| 暂停、修订和重启 | 暂停不自动解除，受影响版本重新计时，原窗口不被无故重置 |
| 重复启动或启动回执前崩溃 | 核对原实例，不创建第二个有效作业 |
| 心跳丢失但作业存在 | 先恢复核对，不立即重派 |
| 并发预算、资源和未知费用 | 不超卖已确认配额，未知不按零结算 |
| 生产产物尚可被写入 | 不进入可信冻结评估 |
| 快检失败、噪声内波动、设施故障 | 不奖励收益，不发负优化黄牌 |
| 同一证据和第二张黄牌 | 不重复发牌，第二张终止对应谱系且保留档案 |
| 真实性疑点与确认违规 | 疑点待核查，确认后准确终止违规实例 |
| 取消和 tmux 观察窗格关闭 | 取消核对真实子作业；观察窗格不决定实验生命周期 |
| 存储超限或归档失败 | 显式阻塞，保留唯一证据，不提前回收 |
| 完整真实任务 | 合同、讨论、放行、执行、评估、决策和交付可追溯 |

不默认运行整仓旧领域回归；以所复用底层和新用户路径为范围。
真实后端调用、容器部署、长编译和 GPU 验收需要明确授权，优先最小有判别力的检查。
必要环境缺失时交付实现与准确的未验证清单，不宣布系统已可无人值守运行。

## 16. 后续 AI 执行约束与交付格式

- 本文件是待办合同，不是授权无条件一次部署全部系统。

- 不为追求快速交付绕过私有数据、预算、权限、停止或唯一证据保留边界。
- 不默认提交、发布、安装、启动或停止用户服务；这些操作按用户的明确要求执行。

每次交付只说明：完成了什么、实际做了哪些必要验证、哪些仍未验证或阻塞，以及下一项真实前置条件。
最终交付应是一个入口、一套账本、一条研究工作流，而不是新旧框架叠加。

| `discussion.py` | 独立提交、评分锁定、精确 0/N 轮回应、角色可见性、静态/增量 Prompt 组装 |
| `reports.py` | 从账本组装双报告、通知后计时、版本与范围绑定、批注、部分放行、草稿恢复 |
| `jobs.py` | 前置/实施任务、依赖、技术确认、预算预留、派发与停止意图、回执、对账和收益政策 |
| `controller.py` | 单所有者 tick/显式前台循环，恢复阻塞、截止与批注处理、按需进度检查 |
| `store.py`、`cli.py` | 新操作入口、指令生命周期、合同改动止派、报告备份恢复和审计 |

### 18.2 没有推理代码时的准备路径

可以先保存目标和部分合同。
要进行实际调研，仍须明确模型预算、并发、期限、允许服务、数据范围、存储额度和对应角色。
前置调研不要求先填出已有推理代码、性能基线或 rebuttal 轮数；后者在进入讨论前由用户确定。
正式实施和收益判断仍要求设备范围、基线、评估协议及实际可生效的运行边界。

当前任务协议支持：

1. 主持人/项目经理分配 source-only 准备任务，调研者或蒸馏者负责。
2. 准备任务交付后，由不同的只读评审角色检查来源与证据。
3. 主持人/项目经理依据捕获的独立评审结果接受或要求继续，不采用工作者自报完成。
4. 用户显式修订合同，补入选定基线、协议和专家指令。
5. 只有尚未开始讨论、没有活动准备作业的草稿轮次，才可显式重新绑定新合同。
6. 进入讨论后配置和合同继续保持版本边界，不悄悄重新解释既有提案与批准。

准备任务的 source review 不产生性能成绩，也不发负优化黄牌。
上述执行者/评审在本批仅实现请求与回执协议，**没有实际调用 Copilot 或访问资料服务**。

### 18.3 讨论和报告控制

- 每个提案有独立 idea ID 和版本，每个方向分别评审，不再固定十二选一。
- 角色投影隔离专家首轮；评审本轮未完全锁定前只收到自己的评分。
- 评分程序计算共同权重、半分步长、平均数和分歧，不将缺失评分填零。
- 0/N 轮包含不修改提案但真实回应的情形；不会缓存旧分数来跳过复评。
- Prompt 将稳定合同/角色指令与本次变化分开，知识按引用提供；评审调用要求明确 idea 范围。
- CLI 导入提案、评分和回应明确标为 `operator-import`，不得称为真实独立 Agent 的执行记录。
- 报告保留提案、回应、评价轨迹和来源状态，预期收益明确未实测。
- 双报告存在且通知回调成功后才计时；通知失败不启动窗口。
- 已交付报告不原地改写；未交付草稿可从数据库恢复，不重复生成不必要版本。
- 批注在短事务中记录；对应范围保持暂停，旧计时器不会清除用户暂停。
- 针对一个方向的重新报告只重启该方向窗口，其他范围保持原截止。
- 针对一个方向的明确批准不解除全局暂停下其他方向的限制。
- 超时放行每个报告/方向版本只登记一次，只允许经理组织任务，不启动外部作业。

### 18.4 任务、预算、回执与停止

- 任务只能依赖本轮已存在的任务；依赖接受后才可准入，避免循环或跳过上游验收。
- 实施任务需要所属方向放行、经理分配和对应专家/工程师确认。
- 同一可写工作区不能同时给两个活动请求使用；逻辑并发额度和费用同时检查。
- 金额用整数微美元记账：预算额度保守向下取整，请求预留保守向上取整。
- 全项目已花/预留/未知费用保留，不因新建轮次或修订合同自动清零。
- 在事务中预留并生成持久启动意图；**控制器目前不会执行启动意图**。
- 请求保留任务与实际分发指令快照；晚到的一次性指令不会被未接收它的旧请求消费。
- `starting` 与 `recovering` 不能重复派发；发现未知实例时阻塞全局新准入。
- 已知未派发请求取消后可以释放预留；已发出请求先登记停止意图，确认结束后才结算。
- 运行器回执绑定准确实例，重复相同回执不重复结算，冲突回执显式拒绝。
- 未知费用继续保留预算；迟到费用通过独立结算路径处理。
- 每小时检查以作业开始为锚，漏过多个周期只补当前必要检查，不召开多次空会议。
- 变更用户合同、暂停或取消本轮时止派并登记相关停止请求；不会按进程名称批量停止任何东西。

CLI 没有开放“伪造启动/完成回执”“导入实测并标为可信”或“自行确认真实性违规”等操作。
这些内部接收函数需要以后由经过隔离和身份核验的运行器/评估器接入。
本批对它们的测试输入都是明确标注的合成回执，不代表真实进程状态或实验结果。

### 18.5 独立评估和处罚的程序部分

- 正式数值测量只接受已完成的独立 evaluation 作业，绑定冻结的生产输出、基线和协议。
- 观察数、噪声与退化规则在任务分配时记录，不能在看到结果后换条件。
- 必须保留匹配的原始结果、命令和环境，不只保存均值。
- 快检失败/未执行/未知、观测不足和干扰明确归为无效比较，不奖励收益或发牌。
- 测量结果不自动接受任务；经理还须作出明确决定，旧尝试成绩不能认证新尝试。
- 同一负优化评估不重复发牌；首张暂停并记录会诊调整，新尝试仍属原方向。
- 第二张停止该方向，保存两次依据；新的同名角色或后续好成绩不清空计数。
- 经可信核对可记录处罚撤销，但不删除历史、不自动复活原尝试。
- 真实性疑点先冻结采用；确认、排除和普通失败分开记录，不把监督指控直接当作证明。
- 确认违规登记对应实例的终止/撤权请求，不连带推定其他角色违规。

真实快检程序、推理 benchmark、可信来源核对、撤权以及进程实际终止仍未接通。
代码中的停止状态与意图不能代替服务器上的终止确认。

### 18.6 备份、恢复和 CLI

版本 2 备份保留规范双报告正文，恢复可重建报告文件并核对 SQL 引用。
恢复到新目录后报告需要重新建立可访问通知，保留原截止，不重新赠送 20 分钟。
报告正文保留历史记录；当前访问地址以 `report show` 的路径字段和恢复通知为准。
已有活动请求恢复为待核对状态；不因数据库重新打开就重派。

**当前备份不是完整推理实验快照。** 源码、模型、数据、原始测量文件、容器/镜像及物理工作区的归档与引用回收，
仍须在实际运行器和产物接收路径中实现并验收；不能据此删除任何唯一原始产物。

新增入口动作：
